# Feedback B1: a Social Security start age past 70, if the law changes (plan, 2026-11-15)

Item B1 of `docs/superpowers/specs/2026-11-15-first-user-feedback-plan.md`. US planner only. One PR, stacked on Tier A
(PR #100). Badge: US V179 → V180. Canada untouched (its badge stays V84).

**What it models.** A law that raises the *earliest* claiming age, so nothing is paid before, say, 72. A cut cannot model
that (it is a later start, not a smaller check). A raised *full* retirement age, which still lets people claim at 62-70
for less, is B2's cut, not this.

The work is the input limit, its clamp, and the copy.

## The design

### The field

- Key `ssLateStartEnabled`, `defaults` value `false`. FIELDS entry (after `ssStartAgeB`):
  `{ key: 'ssLateStartEnabled', type: 'bool', sync: 'controls', resync: ['controls'], onChange: () => clampSsStartAges(state), mcp: true }`.
- The two start-age entries become
  `{ key: 'ssStartAgeA', type: 'number', min: 62, max: SS_START_AGE_MAX_LAW_CHANGE, resync: true, onInput: () => clampSsStartAges(state) }`
  (and B). `min`/`max` on a FIELDS number entry are read only by `mcpAccepts` (checked: `grep -rn "field\.min\|field\.max" src`),
  so they set the MCP limits to 62-75; the switch's own limit is applied by the clamp below. `resync: true` makes the
  listener run `syncControls()` after the clamp, which rewrites the box when the clamp changed the value (the focused-box
  guard skips only an unchanged number).

### The limit and the clamp: a new module `src/us/core/inputs/ss-start-age.js`

```js
// US Social Security start-age limit: 70, or 75 under the "if the law changes" switch (feedback B1)

  export const SS_START_AGE_MAX = 70;
  export const SS_START_AGE_MAX_LAW_CHANGE = 75;
  export const ssStartAgeMax = (s) => (s.ssLateStartEnabled ? SS_START_AGE_MAX_LAW_CHANGE : SS_START_AGE_MAX);
  // Lowers a start age above the limit to it. Only the top is clamped: the box's minimum of 62 was never enforced, and a
  // half-typed age ("7" on the way to "72") must not jump to 62.
  export function clampSsStartAges(s) {
    const max = ssStartAgeMax(s);
    for (const k of ['ssStartAgeA', 'ssStartAgeB']) if (s[k] > max) s[k] = max;
  }
```

It takes the state object as an argument and imports nothing, so `normalizeState` (on the object it builds) and the
hooks (on the store's `state`) share it. It is not in the engine closure (no engine module imports it). `core/inputs/`
is the topic folder for input rules. `npm run analyze` updates the module map.

### Where the clamp runs

1. **`normalizeState`** (load, undo, reset, import, `w.setState`): after the FIELDS loop, the migration below, then
   `clampSsStartAges(s)`.
2. **Typing** in a start-age box: its `onInput`. Off: "72" becomes 70 at once and the box shows 70. On: 76 becomes 75.
3. **The switch**: its `onChange`. Turning it off lowers a start age above 70 to 70; turning it on changes no age.
   `field-listeners.js` gets one line in the bool/choice `change` listener, before the resyncs:
   `if (field.onChange) field.onChange();` (shared; no other entry has `onChange`, so nothing else moves). The FIELDS
   doc paragraph in `docs/architecture/inputs-and-ui.md` adds `onChange`.
4. **The MCP tool** (`src/shared/ui/mcp-tools.js`): after its writes, it runs the hook of every field it wrote
   (`onInput` for a number, `onChange` for a bool or choice), once each, in registry order, *after all the writes*, so a call that sets
   `ssLateStartEnabled: true` and `ssStartAgeA: 73` together keeps 73 whatever the order of the writes. The existing
   retirement-age lines stay. **Side effect (both planners):** an MCP write of `ageA/B` or `lifeExpectancyA/B` now runs
   the same life-expectancy clamp typing runs (today MCP can set a life expectancy below the current age), and
   `profitSharingPct*` its 0-25 clamp (already enforced by its `min`/`max`). No other number entry in either registry
   has an `onInput`. This is the one Canada-visible change; no Canada number moves except through MCP. *Alternative
   for the reviewer:* restrict the hook pass to US by a flag, if the owner wants Canada byte-identical.
5. **`syncControls`** (US): sets each start-age box's `max` attribute to `ssStartAgeMax(state)`, so the browser's
   spinner and the drag gesture stop at the limit. Sync writes only the DOM, never state.

### Old saves: the migration

Today a saved (or typed) 72 is used as-is. Clamping it to 70 on load would move that projection. So in `normalizeState`,
before the clamp: a raw state with no `ssLateStartEnabled` key (any save before V180) and a start age above 70 opens
with the switch on:

```js
if (raw && raw.ssLateStartEnabled === undefined && (Number(raw.ssStartAgeA) > 70 || Number(raw.ssStartAgeB) > 70)) s.ssLateStartEnabled = true;
```

Then the clamp lowers anything above 75 to 75 (a save with 80 moves; ages above 75 were never offered by the box). The
B start age counts even in single-person mode (it is kept, hidden, and returns when the plan goes back to a couple).
Every existing Vitest household and UI script uses start ages of 62-70 (`grep -rn ssStartAge tests test_*.js`), so none
moves.

### The Monte Carlo seed

`ssLateStartEnabled` is added to the names left out of `monteCarloSeed` (with a comment like its neighbours'): the
engine never reads it (the ages carry its effect), and the new key would otherwise change every US seed and move every
Monte Carlo figure and snapshot. The result cache's JSON key includes it, which is harmless (a different key is only a miss).

### The markup (`src/us/index.html`, right after the `ssStartAgeB` field)

```html
<div class="field"><label for="ssLateStartEnabled"><input id="ssLateStartEnabled" type="checkbox"> If the law changes: allow a start age past <span class="info-nw">70<button type="button" class="info-tip" aria-label="More info" aria-expanded="false" data-tip="…">i</button></span><small>Raises the start-age limit from 70 to 75</small></label></div>
```

Not `data-partner-b`: it governs A's age too. Bubble text:

> For a what-if where the law raises the earliest age Social Security can start, so nothing is paid before, say, 72.
> Under today's rules no delayed-retirement credits accrue after 70, so waiting past 70 only loses checks. Enter the
> monthly benefit you expect at the later age, in today's dollars; it is used as-is from the start age, like any other
> start age. A higher full retirement age, which still lets you claim at 62 for less, is a benefit cut, not a later
> start. Turning this off lowers any start age above 70 to 70.

(The "benefit cut" sentence names no field yet: B2's field does not exist. B2 adds "(see the benefit cut field)" when it lands;
the B2 entry of the spec gets that note.)

The existing start-age bubbles (A and B) get one sentence appended: "From 62 to 70; past 70 only with the 'If the law
changes' switch below." The rest ("used as-is ... enter the benefit your SSA estimate shows for the age you plan to
claim") still reads right.

The group summary (`render-group-summaries.js`, "SS at 72") needs no change.

## Tests

**Vitest** `tests/unit/us/ss-late-start.test.js` (new; through `world()`, exact comparisons, hand-computed figures):

- *On, 72:* single, age 65, retired, `ssMonthlyA: 2000`, `inflation: 0` (so the factor is 1; checked in the factor
  code before writing the expected value), `ssLateStartEnabled: true`, `ssStartAgeA: 72`: the state keeps 72; every row
  before age 72 has `ss` 0; the row at 72 has `ss` 24000 (2000 × 12), and so does 73.
- *Off clamps:* the same with `ssLateStartEnabled: false` explicitly: `ssStartAgeA` is 70; the row at 70 has 24000 and 69 has 0.
- *On clamps at 75:* `ssStartAgeA: 80`, switch on → 75.
- *Migration:* a raw state without the key and `ssStartAgeB: 72` → the switch on, 72 kept; without the key and 68 → off, 68.
- *Hooks:* `clampSsStartAges` on `{ ssLateStartEnabled: false, ssStartAgeA: 72, ssStartAgeB: 60 }` → 70 and 60 (the
  bottom is not clamped).
- *Seed:* `monteCarloSeed` is the same for a state with `ssLateStartEnabled: false` and the same state with the key deleted.
- *Survivor symmetry:* identical partners (both 62, retired, start 72, switch on, 2000 a month, inflation 0),
  `survivorEnabled`, death at 75: the rows with `survivorPartner: 'A'` and `'B'` agree on `ss`, `tax` and the end
  balance in every year (`toBe`, two runs in one process); and the survivor's `ss` is 24000 after the death (the greater
  of two equal benefits), 48000 at 72-74, 0 before 72.

Counted with `makeCounter` (`NEW_COUNT` fixed once it runs); run alone and shuffled before the commit.
