# Feedback B2: a Social Security benefit cut, as a what-if (plan, 2026-11-15)

Item B2 of `docs/superpowers/specs/2026-11-15-first-user-feedback-plan.md`; the full spec is Batch 6, item 5
("Trust-fund benefit-cut scenario") in `docs/next-batches-plan.md`, pulled forward on its own (it needs none of the rest
of Batch 6). US planner only: the Batch 6 item is under "Social Security (US)", and Canada's CPP/OAS have no trust-fund
cut in the spec, so Canada is untouched (badge stays V85). One PR against `main` (B1, PR #101, merged). Badge: US V180 → V181.

**What it models.** A law change, or the trust fund running out, that pays a share of scheduled benefits. It also
models a higher *full* retirement age: people could still claim at 62-70, for less at each age, which is a smaller
check at the same start age. A raised *earliest* claiming age is B1's switch instead (a later start, not a smaller check).

## The Trustees figures, checked 2026-11-15

The 2026 OASDI Trustees Report (released June 2026): the OASI trust fund's reserves are depleted in the fourth quarter
of 2032; continuing income then pays about 78% of scheduled OASI benefits (falling to about 62% by 2100). Combined
OASDI (hypothetical): depleted in the third quarter of 2034, then about 83% payable. Sources: SSA, 2026 Trustees Report,
sections II.D and II.E (`https://www.ssa.gov/OACT/TR/2026/II_E_conclu.html`, `II_D_project.html`; the pages refused a
direct fetch here, the figures are from their search extracts) and CRS IF13256, "Social Security: Selected Findings of the
2026 Annual Report" (2026-06-25: OASI Q4 2032; OASDI Q3 2034, 83%). They match the Batch 6 spec. The preset is the
OASI figure, the one retirement benefits are paid from: a 22% cut from 2033 (the first full year after a Q4 2032
depletion). The 78% is the payable share in the depletion year; later years fall slowly. The preset is a flat cut
(the spec's design); the bubble says it is "about".

## The design

### The engine: one share per year, applied where the benefit is computed

In `src/us/core/income/social-security.js`:

```js
  // The share of scheduled Social Security paid in projection year `year` (feedback B2): 1, or 1 less the benefit cut from
  // January of its start year on (a what-if: the trust fund running out, or a higher full retirement age). One factor per
  // year, so C4's means test can multiply its own per-year share in here later.
  export function ssPaidShare(ctx, year) {
    const pct = ctx.inputs.ssBenefitCutPct;
    return pct > 0 && ctx.taxYear + year >= ctx.inputs.ssBenefitCutStartYear ? (100 - pct) / 100 : 1;
  }
```

`socialSecurityIncome` takes `year` in its argument object and multiplies each partner's benefit by the share, after
`factor`: `... * factor * paid`. At the default the share is exactly 1 and `x * 1 === x`, so no existing figure moves
by even a bit. `(100 - pct) / 100` (not `1 - pct / 100`) so 22% gives the double nearest 0.78 (24,000 × it is 18,720 exactly;
checked in Node). The survivor max is taken after the cut, which is the same as cutting the max. Callers:
`run-projection.js:431` and `sankey-columns.js:114` pass `year`.

The cliff plan's estimates take the same share: `ssAt(inputs, p, a, factor)` becomes `ssAt(inputs, p, a, factor, paid)`
with `benefitIncomeAt` passing `ssPaidShare(ctx, y)` (computed once per call, for both partners); `lambdaEstimate`'s
`ssOf` multiplies by `ssPaidShare(ctx, ys)` (computed once per sample, before the `ssOf` calls). Without this the plan
would size conversions against benefits the run no longer pays. At the default both are `× 1`, so they move nothing.

Hot path: one comparison and, when the cut is on, one division per call; nothing is allocated. `ctx.inputs` only, so the
result caches (keyed on the inputs' JSON) key the cut with no change. No new module-level mutable, no snapshot field
(nothing is mutated), so `engine-purity.json` and the MAGI-iteration rules are untouched.

**For C4 (not built):** C4's means test reads the previous year-end balances, a loop value, not an input. It will
pass its own per-year share into `socialSecurityIncome` (for example a `meansShare` argument) and multiply it into
`paid`; `ssPaidShare` stays the input-driven part. Noted in the C4 entry of the feedback spec.

### The fields

- `ssBenefitCutPct`, default `0`; `ssBenefitCutStartYear`, default `2033` (`src/us/core/inputs/defaults.js`, after
  `ssLateStartEnabled`).
- FIELDS (after `ssLateStartEnabled`):
  `{ key: 'ssBenefitCutPct', type: 'number', min: 0, max: 100, onInput: () => clampSsBenefitCut(state) }` and
  `{ key: 'ssBenefitCutStartYear', type: 'number', min: 2000, max: 2200 }`.
  The percent's `onInput` clamps 0-100 on typing (and after an MCP write, which `min`/`max` already bound), as profit
  sharing does, and writes the box when it changed. The year is not clamped on typing (a half-typed "20" on the way to
  "2035" must not jump), only on load.
- New module `src/us/core/inputs/ss-benefit-cut.js` (input rules, beside `ss-start-age.js`; imports nothing; not in the
  engine closure):

```js
// US Social Security benefit-cut what-if: the Trustees' preset and the input clamps (feedback B2)

  // The 2026 OASDI Trustees Report (June 2026): the OASI trust fund is depleted in the fourth quarter of 2032, and continuing
  // income then pays about 78% of scheduled benefits. Revisit all three with every annual Trustees Report.
  export const SS_TRUSTEES_CUT_PCT = 22;
  export const SS_TRUSTEES_CUT_START_YEAR = 2033;
  export const SS_TRUSTEES_REPORT_YEAR = 2026;
  export const SS_BENEFIT_CUT_YEAR_MIN = 2000;
  export const SS_BENEFIT_CUT_YEAR_MAX = 2200;
  // The percent: 0 to 100 (a non-number is 0). The start year (normalizeState only): a whole year in range, else the default.
  export function clampSsBenefitCut(s) { ... }       // percent only, on the object passed; returns true when it changed
  export function normalizeSsBenefitCut(s, fallbackYear) { ... }  // percent and year
```

- `normalizeState`: after the B1 lines, `normalizeSsBenefitCut(s, defaults.ssBenefitCutStartYear)`: the percent to
  `Math.min(100, Math.max(0, Number(x) || 0))`, the year to `Math.round(Number(y))` clamped to 2000-2200, or 2033 when not
  finite. A save without the keys gets the defaults (0, 2033): no cut, so it does not move.
- The FIELDS `max: 2200` / `min: 2000` are literals (FIELDS is a load-time literal), as B1's start ages are; a comment
  names the constants.

### The Monte Carlo seed

Both keys are left out of `monteCarloSeed` by name (comment like B1's): the default would otherwise change every US seed
and move every Monte Carlo figure and snapshot; and with the cut on, the same seed means the same market paths with and
without the cut, so the Monte Carlo difference is the cut's alone. The result cache key (the inputs' JSON) still includes
them, so a cut is never served a cached uncut result.

### The stored-plan fingerprint

`fingerprintJson` drops both keys while the percent is 0 (no cut: the start year has no effect either) and keeps them,
appended after the rest, when it is above 0. At the default the JSON is today's, so every saved `madeFor` still
matches; with a cut set, a plan applied without it reads "computed for different inputs", which is correct (the cliff
plan reads the cut). The search key follows (it is built from the fingerprint).
